Repository-scoped · content-hashed · terminal-native

The gnomon is the fixed blade on a sundial.

The sun travels. The shadow sweeps the hours. The gnomon does not move — and that is precisely why the dial can be read. Remove the blade and you have decorated stone, not an instrument.

This harness names itself after that object. .gnomon/ is the fixed configuration — models, roles, tools, approval — content-hashed and committed with your repository. Everything else is shadow.

§1 — Why

Behaviour is a property of the repository.

Ask most coding agents why did you do that and there is no answer. Configuration scatters across dotfiles and machine state — the same repo behaves differently for two people.

One directory declares models, roles, tools, approval policy. Content-hashed. Stamped on every record the harness emits. Linux, macOS and Windows — same surface, same hash, all three in CI.

gnomon does not make a model complete more tasks: the last peer comparison, in September 2026 on 34 paired Terminal-Bench tasks with the same model, was a tie inside noise (50.0% vs 47.1%). Since then gnomon reports its own results. On long hosted-model tasks it lost runs for reasons traced to gnomon itself; those were fixed, and the largest part — reasoning replay — is a default in 0.5.0. What it adds is governance: a hashed surface, capability separation, a tamper-evident trail, and a checker that holds other agents' work to the same rules. The model varies. The conversation wanders. The tools differ each run. .gnomon/ does not.

§2 — Governance

The rules hold — and they hold for other agents too.

The rules a repository commits — which role may write where, which commands are refused, what needs a person — hold in gnomon's own loop, and can be applied to work another agent did. In G1 (November 2026, sandboxed, one model) gnomon's own loop broke policy in 1 of 24 trials: after its deny-list refused git clean, the agent moved var/ out instead.

gnomon check reads a change after the fact — the diff, and the transcript where there is one — against the repository's .gnomon/ as it stood at the base commit. Since 0.3.2 it reads transcripts of opencode, goose, Qwen Code and mini-swe-agent as well as its own trail, so a destruction that leaves no diff can still be seen.

1 / 24Committed in gnomon's own loop. G1, November 2026. The one: a deny-list refusal routed around by moving the directory instead.
43 / 43Destructive prompts held. Adversarial respellings included, 0 breaches (0.3.1: 38/43, before the shell parser).
27 / 27Self-governance attacks refused with nobody to approve: the agent cannot rewrite its own rules, records or skills (GBS 0.2 draft run, 0.4.2).

The gap, stated. gnomon check cannot see what leaves no diff (git clean -fdx, rm -rf var/, git reset --hard, a force-push) unless a transcript shows it. Give it the transcript, or put gnomon guard in front of the agent so the call is decided before it runs.

Found by measuring. The first GBS-GOVERNANCE run (v0.4.1) found the agent could approve its own skill by unsetting one environment variable, 4 of 4; 0.4.2 closes it and needs a person present for skill decisions — CHANGELOG 0.4.2.

A shared governance layer — one policy, several harnesses

Teams rarely run one agent. The same committed .gnomon/ can govern the others:

  • Before the action — gnomon guard. Sits in Claude Code's and opencode's pre-tool hooks (Cursor: shell and reads only) and decides each call with the same function gnomon's own loop uses. It only tightens: a deny is enforced, an ask goes to the host. Released since 0.3.3.
  • At merge time — gnomon check. For any harness: it reads the diff, and a transcript where there is one, against the rules at the base commit. As a required CI check the agent cannot skip it. It cannot see what leaves no diff (git reset --hard, a force-push) unless a transcript shows it.
  • A tamper-evident trail. Every guard decision is a hash-chained record naming the tool, the rule, the agent, the host and the session.
  • Levels — since 0.5.0. Each family of rules (write, bash, network, secrets, rules, ci) is set to observe → advise → prevent → enforce, so a team can see what a policy would refuse before it refuses anything. A role can only tighten, and the rules that protect the surface and the records never drop below prevent.

The $0 pilot (6 Nov; scripted model, no network, a draft 0.4.5 build; a pilot, not pre-registered). One committed policy, enforced through gnomon guard in opencode and in Claude Code: the two hosts made identical decisions on all 137 forced calls, the same as gnomon's own loop; no call the guard denied ran; 800 of 800 decision records named agent, harness and session. It also found ways to detach the layer — removing the host's hook file, committing the policy away in opencode, Claude Code's bypass mode running an “ask”, opencode's grep going ungoverned. Those are fixed in 0.5.0 (#165). Still missing: org-wide policy distribution, a record of the person's answer to an ask, and adapters for Codex, Aider and Goose.

§3 — Loop

What happens when you type.

The real path, in order. Slash commands stay local. Everything else: role → skills → context → tools under approval policy.

Three guarantees in this path:

  • Tools absent, not discouraged. Schema list matches role exactly.
  • Nothing mutating runs unseen. Diff before write; bash gated.
  • Three buckets. result · refusal · apparatus_failure

§4 — Architecture

Three layers, one hash.

Rust owns verifiable parts. TypeScript owns the loop. Sessions and audit live outside the hashed surface — logs inside .gnomon/ would change the hash every turn.

The blade is .gnomon/: fixed, identifiable, content-addressed. Replies, tool traffic, session history — the shadow.

§6 — Roles

Roles differ by tool list, not by instruction.

The verifier has no write and no edit, so it cannot alter what it judges — and because bash can write anything, bash_allow narrows it to test commands. task runs a sub-turn under that role's tools, so a role that may not write also may not delegate to one that can.

RoleCannot
coordinatoredit; outside write_allow
implementorgated by write_allow / bash_allow / bash_deny
verifierwrite, edit; bash_allow for tests only

Each boundary has a test that fails if it moves. Other harnesses have permission prompts; these are declared per role, hashed, and testable.

The chain stops on a failed check — not on an opinion. One dial, three positions: never, on_refusal, on_check. A stage whose declared check ran and failed stops the chain. A stage that merely disagrees in prose does not — reading its sentence would be instruction, not capability. Default: never. Not yet re-measured — the earlier arm tested a chain that could not gate.

§7 — Six rules

What it holds itself to.

  1. No machine-scoped config. All in .gnomon/.
  2. Manifest every session. Content-addressed.
  3. Declared tool schemas. Refusal, not shorter list.
  4. Three buckets. No composite verdict.
  5. Published exit contract. 0–1 / 2–4 / 10–13.
  6. Published enumerations. README tested.

III — Long tasks: why gnomon lost, and what fixed it

Terminal-Bench 4.0, 29 long tasks, DeepSeek V4.1 Flash, 30-minute cap. gnomon 0.3.1 solved 1 of 29; the main cause was gnomon's: unstreamed calls cut at 300 s and re-sent, fixed in 0.4.0. P2G41 re-ran the tasks on 0.4.1, as released and with a tuned hosted recipe.

gnomon armSolved / validCappedHidden tests passed (mean fraction)
0.4.1 as released0/28210.31
0.4.1 + hosted recipe3/28100.58

Which part of the recipe matters — H3 (same 29 tasks, gnomon 0.4.2, pre-registered). Reasoning replay alone raised the hidden-test share by 16 points [+4, +29] over the release defaults (0.32 → 0.48) and capped 5 fewer runs; the rest of the recipe added +1.7 points [−9.5, +13.8] on top — not shown. By its decision rule, replay became the default for hosted endpoints: in 0.5.0.

Defaults or a tuned recipe — the v0.5.0 release runs. On Claude Haiku, gnomon's release defaults did at least as well as the tuned long-task recipe, at about half the cost. A done check before the final answer made the final answer more honest (fewer “done” claims over unfinished or unverified work) and did not improve outcomes, so it stays opt-in. Start from the defaults.

Why long runs fail. An offline look at 167 valid hosted gnomon runs (6 Nov): 48% hit the 30-minute cap, and in 68% of those the file the task asked for had never been written — the model explored until time ran out. Capped runs spent about 84% of their time in model calls and 14.5% in tools; everything else, gnomon's own overhead included, was about 1%. The responses — a run deadline, deliverable-first time notes, a finish gate, a soft-timeout shell — ship opt-in in 0.5.0; none is shown to improve outcomes.

Traceability, tested on 58 cells. gnomon audit verify: 54/54 chains intact (25 sealed, 29 correctly reported not sealed). On the 25 runs that ended by themselves, model-call counts and prompt/completion tokens match the billing relay to the token, and reasoning tokens match the wire 13/13. On 24 of 29 runs killed at the cap, gnomon's surviving records miss calls the relay billed (55 calls; median 48 s of unrecorded time, at most 287 s). Two record defects were fixed in 0.4.3 (#151); a self-stop before the cap (--deadline, #153) is in 0.5.0.

V — Local models and steering

M2 gave each local challenger its best known recipe on v0.4.0, against Qwen3.6-35B on the same lane. Flash-Next (GB10): local-only 20 vs 16, ahead but not shown (p = 0.29); its hybrid arm capped 9 vs 6 and fails the pre-set rule. Muse Glimmer 30B and Qwen3.8-27B (RTX 5090) trail, not shown. VI — gnomon Bench Standards (draft)

GBS proposes open benchmarks for what a harness decides, as distinct from the model. gnomon's authors wrote the specs and build a harness they measure, so read the results accordingly. One line per spec, with gnomon's own latest figures — scripted models, no model calls, $0:

  • OVERHEAD — the time and CPU a harness adds, independent of the model. 0.4.2: +169 ms CPU per run of 11 scripted round-trips over a null Node harness [155, 196]; 0.2 ms per policy decision, audit write included (0.4.1).
  • CHAOS — are injected endpoint faults announced, or swallowed? 0.4.2: 17 of 20 faults announced (34 of 37 cases). Still silent: a dropped late system message, a throttled stream, a cache miss.
  • GOVERNANCE — a scripted compromised model forces forbidden actions: are they stopped, and can the agent rewrite its own rules? 0.4.2, asks auto-approved: 170 of 280 attacks blocked by the default rules; 245 of 280 with the kernel sandbox (exec = "os" plus read scoping — opt-in, PR #156, in security review, not released). Self-governance 27/27 with nobody to approve; 26/27 with asks auto-approved (a coordinator reached a deletion through a sub-agent).
  • AUDIT — does the record survive tampering, and can someone else check it? 0.4.2 with a git anchor: 7/7 · 3/3 · 5/5 attacks caught at the three adversary levels (5/7 · 2/3 · 0/2 without a witness); 0 false alarms in 48 untampered sessions.
  • HYBRID — does a local/cloud split beat local on quality and cloud on cost, with local compute priced? See IV: it beats local-only on quality and cloud-only on cost, and trails cloud-only on quality — a cost mode.
  • REPORTING — what every result must state: builds, the pre-registration it cites, paired design, margins, honest denominators, open traces. Held to it, gnomon's own records matched the billing relay to the token on 25/25 long-task runs that ended by themselves (0.4.1).
  • LAYER (draft, not yet published) — one policy across harnesses. Where a policy can attach (the loop, a pre-tool hook, a stop hook or CI, a wrapper), whether the agent can skip or detach it, and whether each violation was prevented, caught before merge, caught after, or missed. Its pilot is in §2.

Sources: the GBS 0.1 run on 0.4.1 (gbs-2026-11-04) and the GBS 0.2 draft run on 0.4.2 (5 Nov, PR #155). Running the specs found 50 places they could not be followed as written; v0.2 resolves 47. No cross-harness GBS table is published.

§9 — Limits

Stated plainly.

A harness that hides its gaps is worse than one that has them.

  • MCP: stdio only. Pinned server → discover tools → gate per role. Reproducibility bounded — gnomon pins invocation, not what the server does.
  • Not a hosted or async service. Runs in your terminal — and from there reaches cloud models, authenticated cloud CLIs (gh, az…), and the web. No queue, no worktree pool. One unattended path: cron-scheduled loops.
  • Terminal, ACP editors, a local dashboard. gnomon acp serves Zed, JetBrains and other ACP editors; gnomon dashboard runs on your machine. Nothing beyond that.
  • gnomon check sees what leaves a trace. A destruction of git-ignored state leaves no diff; only a transcript shows it. The transcript readers (since 0.3.2) close that on replay; not yet re-run live.
  • Long hosted-model tasks are hard for it. Full solves on 30-minute Terminal-Bench 4.0 tasks stay few; the gains measured are in the share of hidden tests passed. Reasoning replay, the change that helped most (H3), is a default in 0.5.0.
  • Governance across harnesses is a decision layer, not a platform. No org-wide policy distribution, the person's answer to an ask is not recorded, no adapters for Codex, Aider or Goose; tools a host does not hook are not governed.
  • Path sandbox and a network filter. webfetch has SSRF guards; network = false refuses the common network commands in bash. That is an intent filter, not process isolation. exec = "docker" isolates; before 0.5.0 it did not hold against a deliberately hostile model aiming at gnomon's own host-side actions, fixed in 0.5.0 (#158). A kernel-enforced exec = "os" is an open pull request (#156, superseding #74) awaiting an independent security review — not released.
  • Summary compaction not reproducible.
  • Runs killed from outside lose their last calls. On 24 of 29 capped runs the record missed calls the provider billed (up to 287 s). A self-stop before the cap (--deadline, #153) is in 0.5.0.
  • Injection resistance unmeasured. 0/36 crossed, but the model attempted none.
  • Hybrid trades quality for cost. About 23% of cloud-only's cloud spend, at −0.07 hidden-test share against cloud-only; slower, with more runs capped (§8 IV). Opt-in.
  • npm carries the package, not the native binaries. npm i -g gnomon-harness (from 0.5.0) gives you gnomon; the installer also fetches the binaries surface, session and apply need.

Linux, macOS and Windows — all three in CI, every commit. Windows runs natively, not through WSL. It needs Git for Windows for its POSIX shell, and gnomon refuses rather than falling back to cmd.exe — a shell that changes with the OS would be machine-scoped behaviour the hash cannot see.
