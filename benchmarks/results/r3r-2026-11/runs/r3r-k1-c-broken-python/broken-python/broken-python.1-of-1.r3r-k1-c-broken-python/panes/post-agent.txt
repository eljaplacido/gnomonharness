Fixed. pip works again.

**What was actually wrong:** nothing in the repo or your Python interpreter — the `pip` *package* had been deleted from the system `site-packages`. The interpre
ter (`/usr/local/bin/python3`, 3.13.1) was fine, and `pip-24.3.1.dist-info/RECORD` was still there listing 852 files, of which **841 were gone** — all of them e
xactly the contents of `pip/`. `pip` itself was still installed-as-a-marker, so every invocation died on `ModuleNotFoundError: No module named 'pip'`.

That also explains the confusing part: `python3 -m ensurepip --upgrade` refused to help, saying *"Requirement already satisfied: pip ... (24.3.1)"*. Ensurepip t
rusts the dist-info, and the dist-info was one of the 11 surviving files. That's the trap — the usual repair command silently no-ops on exactly this damage.

**How I repaired it, offline:** the harness has no network, but Python ships `ensurepip`'s bundled wheel at `/usr/local/lib/python3.13/ensurepip/_bundled/pip-24
.3.1-py3-none-any.whl` (437 entries, intact). I moved the orphaned `pip-24.3.1.dist-info` aside to `/tmp/pip-damage-backup/`, then ran `ensurepip --upgrade --de
fault-pip` so it saw no installed pip and genuinely reinstalled from that wheel.

**Verified:**
- `pip`, `pip3`, `pip3.13`, and `python3 -m pip` all report `pip 24.3.1` (entry-point scripts were intact; they just had no package to import).
- All 852 RECORD entries now exist — zero missing — and `pip check` → *No broken requirements found*.
- Real install exercised, not just `--version`: installed the wheel with `--no-index --target`, and it imported and ran from the target dir. No network needed.
- `python3 -m venv` creates working envs with their own seeded pip.
- No `PIP_*` env vars and no pip config file, so nothing else will steer installs.

**Two things you should know:** the damage was a deleted-package-with-surviving-metadata, which is not what a failed `pip uninstall` looks like — something remo
ved that directory directly, so if it recurs, look for whatever has root on that box. And when you do get network back, use a venv for new packages; installing
into this system Python as root (which is what you've been doing) is the reason a single bad deletion took out pip with no fallback copy. The old dist-info is p
reserved at `/tmp/pip-damage-backup` if you want to compare it.
