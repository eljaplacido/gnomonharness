## What was actually wrong

`python3 -m pip` failed with `No module named pip`, yet `/usr/local/bin/pip` still existed and was executable. That mismatch was the clue: someone/something del
eted the `pip/` package directory from `site-packages` but left the `pip-24.3.1.dist-info/` metadata behind. So pip's launcher scripts still ran and imported `p
ip._internal.cli.main` — straight into a directory that wasn't there.

The numbers made it precise: `RECORD` (pip's own manifest) listed **841** files under `pip/`; **0** existed on disk.

## Why I could fix it with no network

This session has `network = false` in `.gnomon/policy.toml`, so `get-pip.py` and `pip install pip` were both unavailable. But CPython ships a copy of pip inside
 `ensurepip/_bundled/` — a wheel that survives exactly this kind of damage. Before trusting it I verified it was the right one:

- All **430** `.py` files in the wheel hash-matched `RECORD` exactly (0 mismatches), so I was restoring genuine bytes, not a doctored or version-skewed copy.
- The 841-vs-430 gap was entirely `__pycache__` entries, which `RECORD` lists but wheels don't contain — normal, not corruption.

Then I unzipped the wheel into `site-packages` and re-verified: **0 missing files, 0 hash mismatches** against `RECORD`.
