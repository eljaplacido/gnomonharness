## What was actually wrong

Not a permissions or network problem — **pip's code was deleted from disk**. In `/usr/local/lib/python3.13/site-packages` the `pip/` package directory was gone,
 while `pip-24.3.1.dist-info/` and the `/usr/local/bin/pip{,3}` launcher scripts survived. So pip looked installed, but every invocation died importing code tha
t no longer existed:

```
ModuleNotFoundError: No module named 'pip'
```

I confirmed the scope by checking the installed `RECORD` manifest: **841 of 850 recorded files were missing** — precisely the 841 entries under `pip/`. The meta
data was the only thing left. There was no `EXTERNALLY-MANAGED` marker, no `pip.conf`, and no proxy variables, so nothing else was interfering.

## The trap worth knowing about

My first repair attempt was `python3 -m ensurepip --upgrade` — the standard fix. **It silently did nothing**, reporting "Requirement already satisfied". The orp
haned `dist-info` makes `ensurepip` believe pip is installed, so it skips the work. If you'd tried that yourself, it would have looked like it succeeded while c
hanging nothing. I verified this reproduces on a fresh venv, and it's why the repair instructions I wrote steer away from it.

## The fix

I re-extracted pip's own bundled wheel (`ensurepip/_bundled/pip-24.3.1-py3-none-any.whl` — the exact matching version, already on disk, no network needed) into
site-packages. That restored all 437 recorded files, with **zero missing**, and the tree byte-compiles cleanly. I backed up the old metadata to `/tmp/pip-dist-i
nfo.backup`.

Verified end to end rather than just `--version`: created a venv, installed `six` for real, imported it, uninstalled it, and confirmed a system-wide install wor
ks too. All test artifacts were then removed — site-packages contains only `pip` and `pip-24.3.1.dist-info`, as it should.

## Regression check

`check_pip_health.sh` in the repo root catches this specific failure mode. It's not a check I only ran against a passing system — I reproduced the breakage in a
 throwaway venv and confirmed it exits **1** and pinpoints the cause, versus **0** on the healthy system. It validates that every file in pip's RECORD actually
exists, which is the check that would have caught this immediately.

One bug I found and fixed in my own script: it originally checked `pip` via `PATH`, so a broken venv was masked by the healthy system pip and falsely reported `
ok`. It now resolves scripts relative to the target interpreter's own `bin` directory.

The repair commands it prints are ones I executed verbatim against a broken venv to confirm they work, not untested suggestions.

Two caveats worth flagging: I never determined *what* deleted the `pip/` directory — if it was a cleanup script, container layer squash, or aggressive disk prun
