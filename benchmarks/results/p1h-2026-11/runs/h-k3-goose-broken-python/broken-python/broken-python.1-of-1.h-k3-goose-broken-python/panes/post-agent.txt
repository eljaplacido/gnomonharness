## Root cause

Your `pip` **launcher scripts existed but the actual `pip` package was deleted.**

`/usr/local/lib/python3.13/site-packages/` contained only leftovers:

```
README.txt

```

The `pip/` directory itself was gone (site-packages was last modified Oct 31 13:45, while the metadata dated back to the image build). So every `pip` invocation

```

Traceback (most recent call last):
  File "/usr/local/bin/pip3", line 5, in <module>
    from pip._internal.cli.main import main
ModuleNotFoundError: No module named 'pip'
```

This is a classic half-deleted install: something removed the package tree but left `dist-info` behind. That leftover metadata is also why the obvious fix fails
 — `ensurepip` checks the metadata first:

```
$ python3 -m ensurepip --upgrade --default-pip
Requirement already satisfied: pip in .../site-packages (24.3.1)   ← lies
```

2. Re-ran `ensurepip`, which then installed cleanly from its bundled wheel:

## Two things worth knowing

- **`/usr/bin/python3` (Python 3.11) has no pip either.** That's Debian's own interpreter, separate from your `/usr/local/bin/python3` (3.13.1) that owns `pip`/
`pip3`. It was already that way and isn't what was broken. If you need it, use `apt install python3-pip` rather than touching `/usr/local`.
- **`setuptools` isn't installed** — that's normal for Python 3.13, whose `ensurepip` no longer bundles it. Modern pip uses build isolation and fetches build ba
ckends on demand, which the source-build test above confirmed. Only install it if you use legacy tooling that does its own `setup.py` imports.

To avoid recurrence, prefer virtualenvs (`python3 -m venv .venv`) rather than installing into site-packages directly — a stray `rm -rf` can't break your interpr
eter that way.
