Fixed. Here's what was wrong and what I did.

## Root cause

Your `python3` is Python 3.13.1 at `/usr/local/bin/python3`. In its site-packages, the `pip` metadata still existed but the actual package code was gone:

```
/usr/local/lib/python3.13/site-packages/
├── pip-24.3.1.dist-info/   ← metadata present
└── (pip/ directory missing) ← code deleted
```

The `pip`/`pip3` launcher scripts at `/usr/local/bin` are still intact, but they start with `from pip._internal.cli.main import main`, so every invocation died
with:

```
ModuleNotFoundError: No module named 'pip'
```

This is a partial deletion — something removed the `pip/` folder while leaving the `.dist-info` behind (an interrupted uninstall, a stray `rm -rf`, or a tool cl
eaning site-packages). It wasn't a permissions or PATH issue, and before I fixed it, `pip install` would fail before it ever reached the network.

## Fix

I reinstalled pip from the wheel that ships with your Python installation (`ensurepip`'s bundled `pip-24.3.1-py3-none-any.whl`) using `--force-reinstall`, which
 replaced the orphaned install cleanly:

```
Successfully uninstalled pip-24.3.1
Successfully installed pip-24.3.1
```

## Two things worth knowing

- There's a **second Python** at `/usr/bin/python3` (Debian 3.11.2) that has **no pip at all**. Your `python3` resolves to the `/usr/local` one, so you're fine,
 but if you ever call `/usr/bin/python3 -m pip` directly it will still say "No module named pip".
- `pip list` shows only pip installed. That's normal for this Python 3.13 build (no `setuptools`/`wheel`), and pip can bootstrap those when needed.

Since this is a system-wide install, any future `pip install` will write into `/usr/local/lib/python3.13/site-packages` as root and can affect the whole system
— a virtualenv (`python3 -m venv myenv`) is the safer route for project work. Optional: `pip install --upgrade pip` to move off 24.3.1 (26.2.2 is current).
