## What was actually wrong

This wasn't a path, permissions, or network problem — it was **partial deletion of the pip package**.

`/usr/local/lib/python3.13/site-packages/` contained:

```
pip-24.3.1.dist-info/    ← metadata: present
pip/                     ← actual code: DELETED (all 841 files gone)
```

The `pip`, `pip3`, and `pip3.13` launcher scripts in `/usr/local/bin/` still existed and were valid — they just crashed on the import:

```
File "/usr/local/bin/pip", line 5, in <module>
    from pip._internal.cli.main import main
ModuleNotFoundError: No module named 'pip'
```

**The nasty part:** the leftover `dist-info` made Python believe pip 24.3.1 was fully installed. So the obvious fix silently did nothing:

```
$ python3 -m ensurepip --upgrade --default-pip
Requirement already satisfied: pip in .../site-packages (24.3.1)   ← lied, installed nothing
```

This is why pip can be genuinely painful to repair — the "already satisfied" check reads metadata, not the actual files.

2. **Backed up then removed the orphaned `dist-info`** so the "already satisfied" check could no longer misfire → `/tmp/pip-orphan-dist-info-backup.tar.gz`.
3. **Reinstalled from the bundled wheel** with `python3 -m ensurepip --upgrade --default-pip` — this succeeded offline, no PyPI needed.
