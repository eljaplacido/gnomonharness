## What was actually wrong

Your Python install wasn't corrupted; it had a **half-finished uninstall**. The `pip` package directory was gone from `site-packages`, but its metadata folder w
as still there:

```
site-packages/
  README.txt
  pip-24.3.1.dist-info/     <- metadata says "pip 24.3.1 is installed"
  (pip/ missing)            <- the actual code is gone
```

`RECORD` in that dist-info listed 852 files including `pip/__init__.py`, none of which existed. So the launcher scripts at `/usr/local/bin/pip` still ran and tr
ied `from pip._internal.cli.main import main` → `ModuleNotFoundError: No module named 'pip'`.

## The trap worth knowing about

The obvious repair, `python3 -m ensurepip --upgrade`, **silently did nothing** — it printed `Requirement already satisfied: pip` and returned success. It reads
that stale dist-info and concludes pip is present. That no-op is what makes this state sticky; running it repeatedly looks like it's failing to help.

I had to move the phantom dist-info aside first (backed up to `/tmp/pip-repair-backup/`, not deleted), after which ensurepip installed normally.

## Repair path

No network was needed. The bundled wheel at `ensurepip/_bundled/pip-24.3.1-py3-none-any.whl` matched the missing version exactly, and I verified it before trust

```
mv .../pip-24.3.1.dist-info /tmp/pip-repair-backup/

```
